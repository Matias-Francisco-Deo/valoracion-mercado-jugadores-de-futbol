# Data Model: Player Service

## Entity: Player

| Field | Type | Constraints | Notes |
|-------|------|-------------|-------|
| id | Long | Required after persistence; generated by database | Unique identifier |
| name | String | Must not be blank; unique in the current schema | Player display/lookup key |
| currentPrice | Integer | Must be positive | Follows existing model validation |
| totalTokensIssued | Integer | Must be non-negative | Reflects current model defaults |

## Relationships

- `Player` is a standalone domain entity with no direct relation to the service contract beyond persistence and lookup flows.
- The repository persists instances through the existing `PlayerJPADTO` adapter and maps them back to `Player` model objects.

## Validation rules

- A player cannot be created with a blank or null name.
- A player must have a positive current price when persisted.
- Total issued tokens must not be negative.
- A lookup by id must fail clearly when the player does not exist.
- The service should return all players from the repository in a consistent collection order.

## Repository contract extension

The existing repository interface will be extended to support the list operation required by the feature:

- `Player guardar(Player player)`
- `Optional<Player> recuperar(Long id)`
- `List<Player> listarTodos()`

This matches the current repository naming style (`guardar`, `recuperar`) and preserves service-layer consistency.
